## FINDINGS

1: docs/03-board-generation.md — "fallback board — a committed hardcoded template (gentle S-curve river with 2 bridges near rows 4 and 10, two forests, one line of hills), materialized by the same code as constants." — The doc never gives the actual tile coordinates, brief JSON, or grid for the fallback template, so a phase 4 agent must invent the exact layout. That breaks the "deterministic backup" promise and the snapshot/determinism tests, and two agents could ship different fallback boards.

2: docs/06-api-contract.md vs docs/02-game-rules.md — "player_turn → won (all enemies dead by the player's actions before end-turn)" (status matrix, "the only legal transitions") vs "Called by feature code after applying the player's moves (before scheduling an AI turn) and after applying AI actions." (checkVictory) — checkVictory runs after player moves and can return "enemy" (player army wiped by counterattacks), but the status matrix has no player_turn → lost transition. A phase 5 agent must invent whether a self-wiped player becomes "lost" or is left stranded in player_turn with no units.

3: docs/04-ai-integration.md — "Mock implementation (mockLlm.ts, same interface): returns recorded/fixture JSON responses." — No actual fixture content is specified (what brief or turn response the mock returns), so phase 4/5 agents must invent their own fixtures; two agents' mocks and resulting boards/turns will differ.

4: docs/06-api-contract.md — "Runs board generation (LLM brief + materialization, 03) synchronously; then assembles both armies and inserts the row" vs "409 {"error":"Active game limit reached (5)"}" — It is unspecified whether the active-game cap (409) is checked before or after the synchronous 10–60s board generation; an agent could make the user wait a full minute only to receive a 409, or fail fast before generating.

## AMBIGUITIES

1: docs/06-api-contract.md — `e.g. "move 1: archer cannot attack a unit at 3 tiles"` — Interpretation A: the move index in 400 error messages is 1-based (move 1 = first bundle entry). Interpretation B: it is 0-based (move 0 = first entry). The example shows "move 1" but never states the convention, so two agents' 400 bodies will differ.

2: docs/06-api-contract.md vs docs/05-frontend.md — "moves were already applied atomically by endpoint 13, so ending the turn is pure state transition" vs "[End turn] → POST /moves (staged list) → POST /end-turn" — Interpretation A: POST /end-turn can be called directly without a preceding POST /moves in the same round (ends the turn with zero moves applied). Interpretation B: POST /end-turn requires a POST /moves submission this round and returns 409 otherwise. The docs describe the frontend always calling /moves first but never state backend enforcement.

## CONTRADICTIONS

1: docs/06-api-contract.md — "send ANY ZERO OR MORE of username/theme; at least one key must be present." — The same sentence says an empty PATCH body is allowed ("zero or more") and forbidden ("at least one key must be present"). A phase 2 agent must choose: empty body → 200 no-op, or empty body → 400 validation error.

2: docs/05-frontend.md vs docs/06-api-contract.md — "3 s GET /play/:id while ai_turn" vs "| 11 | GET /api/games/:id | Full game state (+ stale recovery) | yes |" — 05 instructs the client to poll GET /play/:id (a frontend route path), while 06 defines the game-state endpoint as GET /api/games/:id. An agent following 05 literally would poll the wrong URL and receive HTML instead of JSON.

## VERDICT

1. The fallback board template is entirely unspecified (docs/03), forcing a phase 4 agent to invent the exact layout and breaking the promised determinism and reproducibility.
2. The status matrix (docs/06) omits player_turn → lost even though checkVictory (docs/02) runs after player moves and can return "enemy", so a phase 5 agent must invent self-wipe handling or strand a wiped player in player_turn.
3. PATCH /api/me (docs/06) contradicts itself within one sentence ("zero or more" vs "at least one key must be present"), so a phase 2 agent must guess whether an empty body is a no-op 200 or a 400.
