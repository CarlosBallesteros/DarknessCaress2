## FINDINGS
(#: file — quoted line/sentence — what could go wrong when implemented)

1. docs/00-project-overview.md — "Terrain has no mechanical effect in MVP (purely cosmetic). Water is impassable except on bridges."
   The blanket "no mechanical effect" is immediately contradicted by the water exception in the same paragraph. An agent applying the constitution literally makes all terrain passable, which contradicts docs/02-game-rules.md ("lake and river tiles are impassable; bridge is walkable") and breaks movement legality on the board.

2. docs/05-frontend.md vs docs/06-api-contract.md — 06 line 142: "attackTiles = enemy-occupied tiles with distance ≤ class attack range from any tile the unit can finish on — i.e. tiles attackable THIS turn."
   05 lines 68–71: "click a moveTile → client computes + displays the shortest legal path …; overlay now shows the actions FROM THAT destination: attackTiles/red, healTiles/green."
   The API preview returns a union over *every* reachable destination, but the UI shows attack tiles *from the single chosen destination*. The spec never says the client must filter the union by destination, so the board overlay can show tiles the unit cannot actually attack from its chosen final tile — or the backend is expected to return per-destination tiles, contradicting 06.

3. docs/02-game-rules.md vs docs/06-api-contract.md — 02 line 64: `| { kind: "counter"; attackerId: string; targetId: string; damage: number; targetHp: number } // targetId = the counterer`
   06 lines 42–43: `counter: { damage: number; attackerHp: number } | null;  // attacker = this unit`
   The engine's counter event records the *counterer* as `targetId` (carrying the counterer's HP), but the client-facing DTO needs the *attacker's* post-counter HP (`attackerHp`) for damage popups. The event→DTO mapping is unspecified, so HP bars and popups after an AI turn can show the wrong unit's HP.

4. docs/06-api-contract.md — `GET /api/meta` example (lines 102–105) lists only `sword` and `healer` under `classes` (no ellipsis).
   docs/01-architecture.md line 131 says meta "serves the public subset (classes labels/stats/role…)"; docs/05-frontend.md line 99 renders "6 class cards from GET /api/meta". An agent transcribing the example literally ships a 2-class meta and breaks the Champions tab.

5. docs/01-architecture.md — line 137: "skip if a job started for this game in the last 55 s." Config line 127: `"staleAfterSeconds": 60`; line 147 / docs/04-ai-integration.md line 154: re-trigger after 60 s.
   Staleness is 60 s but dedup guards only the last 55 s. A slow LLM turn started 55–60 s ago is neither guarded nor fresh, so a duplicate AI job can launch and apply moves to an already-updated state (a double enemy turn or validation failure).

6. docs/07-assets.md — line 27: "If an expected file is missing at runtime, the component renders its placeholder fallback (see below) and logs one console.warn — never a broken image icon, never a crash."
   "See below" describes generated placeholder *files*, not a runtime fallback UI. What the component actually renders when a file is missing is unspecified; the frontend agent invents it.

## AMBIGUITIES
(#: file — quote — interpretation A vs interpretation B)

1. docs/02-game-rules.md vs docs/06-api-contract.md vs docs/05-frontend.md — 02 line 89–90: "Wait: legal anywhere. A unit given no move stays acted: false … Set acted: true for every unit that received a move."
   06 line 158: "sets acted: true on every moved unit." 05 line 83: end-turn confirm dialog shows "only when un-acted units remain."
   - Interpretation A: any staged bundle entry (including `[wait]`) counts as receiving a move → `acted = true`, so waiting all units suppresses the end-turn confirm dialog.
   - Interpretation B: only units that actually moved/attacked/healed are "moved units" → a pure wait stays `acted = false`, so the confirm dialog appears even when the player deliberately waited everyone.
   This changes confirm-dialog behavior and next-turn legality; the spec does not say which.

## VERDICT
Top 3 findings, ranked, one sentence each.

1. The preview `attackTiles` contract (docs/05 vs docs/06) — the board's core interaction cannot be implemented consistently because the API returns a union over all destinations while the UI expects per-destination attack tiles, with no specified client-side reconciliation.
2. The `counter` event → `AiAction.outcome.counter.attackerHp` mapping (docs/02 vs docs/06) — the engine records the counterer's HP, but the DTO requires the attacker's post-counter HP, so damage popups and HP bars after an AI turn will show wrong values unless the server tracks it (unspecified).
3. The `[wait]` acted flag (docs/02 vs docs/06 vs docs/05) — it is unspecified whether waiting marks a unit `acted`, which flips the end-turn confirm dialog and next-turn legality, so core turn semantics will be implemented two different ways.
