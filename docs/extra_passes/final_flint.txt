# Spec Audit — Darkness Caress II

Scope: I read **only** the ten `docs/` files plus `README.md` you listed, and ignored everything else (including `docs/extra_passes/`). Every quote below is taken verbatim from those reads; no finding was carried from memory.

## FINDINGS

1. **docs/00 (line 73) vs docs/03 (lines 22–25) — river spec contradicts itself.**
   - 00: *"Zero or one river line per board. A river is a connected path across the board with a few **turns** (never a straight canal, never spiraling into a flooded board). Only crossing points are the 1–2 bridges lying on it."*
   - 03: `"bridgeTiles": <integer 1 or 2>,` … *"A river runs from the LEFT edge to the RIGHT edge. It must curve: it may not be straight. 1 or 2 bridges cross it."*
   - What could go wrong when implemented: the Stage‑1 brief zod schema hard‑requires `bridgeTiles` ∈ {1, 2}, and the fallback template is "a gentle S‑curve river with 2 bridges", so a zero‑river board is unrepresentable. The phase‑4 agent must silently pick which rule wins.

2. **docs/06 (line 12) vs docs/06 (line 144) — unit‑ownership error prescribed twice, inconsistently.**
   - 06: *"a game id or unit id not belonging to the caller ⇒ `404 {"error":"Not found"}` — never `403`"*
   - 06: *"Errors: `404 {"error":"Unit not playable"}` (unknown, not owner's, or already acted this turn)."*
   - What could go wrong: one condition ("unit not owned") mapped to two different mandated error bodies; unresolvable without a doc decision.

3. **docs/01 (line 137) vs docs/01 (line 127) / docs/04 (line 154) — stale-recovery guard window contradicts staleness threshold.**
   - 01: *"skip if a job started for this game in the last **55 s**."*
   - 01: `"ai": { "moveRetries": 3, "staleAfterSeconds": 60 },`
   - 04: *"the stale-recovery sweep (01) re-triggers the job after config.ai.staleAfterSeconds (60 s)"*.
   - What could go wrong: the idempotency guard (55 s) and the configured staleness threshold (60 s) are different numbers; the implementer must choose which drives re-triggering.

4. **Gap — docs/09 Phase 1 vs docs/06: `GET /api/health` is mandated but absent from the contract.**
   - 09 Phase 1: *"server boots with `GET /api/health` → `{"ok":true}` (no auth)"*; acceptance: *"[ ] …server boots, /api/health 200"*.
   - 06: no health endpoint in the 1–15 table or conventions.
   - What could go wrong: 08's gap protocol says stop and ask; 09/10 treat it as Phase‑1 acceptance; an agent must invent path, body, and auth.

5. **Gap — docs/00 (line 46) vs docs/01 (line 127): board-design temperature (0.8) has no canonical config home.**
   - 00: *"…difficulty personas + temperatures, board size, games cap — plus the lore strings and the AI-retry knobs; canonical shape in `01-architecture.md`."*
   - 01: `"ai": { "moveRetries": 3, "staleAfterSeconds": 60 },`
   - 03:34 / 04:19: *"Temperature for this call: `0.8`"* / *"temperature 0.8"*.
   - What could go wrong: the brief temperature is specified in prose but absent from the canonical config's `ai` block, so an agent must hardcode or extend the config.

## AMBIGUITIES

1. **docs/02 (lines 92–95) — "partially acted" turn.**
   - Quote: *"There is no 'partially acted' turn. The player may submit fewer than 10 moves (10 = the fixed army size from config); un-acted units simply do nothing when the turn ends."*
   - Interpretation A vs B: A = partial turns allowed, un‑acted units forfeit; B = "no partially acted turn" read as atomic/all‑or‑nothing despite the clarifying next sentence.

2. **docs/04 (lines 82–94) — STATS line format underspecified.**
   - Quote: *"Format, exactly: <class>=hp<hp>/atk<atk>/def<def>/mov<mov>/rng<range>/role<role>"*; *"/heal<n> is appended only for classes with a config healAmount (baseline: /heal8)."*
   - Interpretation A vs B: where the `/heal<n>` token attaches; what an empty range renders as (`rng0`).

3. **docs/04 (lines 130–132) — omitting a unit vs. staging a `wait`.**
   - Quote: *"omitting a unit means it does NOTHING this turn (stays un-acted — equivalent to waiting without an entry)."*
   - Interpretation A vs B: whether omit ≡ wait in `acted` semantics, or whether they are distinct paths.

4. **docs/05 (line 83) — end-turn button semantics.**
   - Quote: *"…button always enabled, confirm dialog only when un-acted units remain."*

## CONTRADICTIONS

1. **docs/00 (line 73) vs docs/03 (lines 22–25)** — zero-or-one river vs. mandatory 1–2 bridges (detail in FINDINGS).

2. **docs/06 (line 12) vs docs/06 (line 144)** — unit-ownership error body (`Not found` vs `Unit not playable`).

3. **docs/01 (line 137) vs docs/01 (line 127) / docs/04 (line 154)** — stale-recovery guard window (55 s) vs staleness threshold (60 s).
