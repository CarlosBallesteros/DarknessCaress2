## FINDINGS

1. **Staged-move payload shape — internally inconsistent (defect).**
   - `docs/05-frontend.md:75`: "…stage {unitId, path, attack:target}…"
   - `docs/02-game-rules.md:29–31` and `docs/06-api-contract.md:159–163`: `"action": { "type": "attack"; "targetId": "E-axe-1" }`
   - What could go wrong when implemented: an implementer following the frontend doc stages `attack`; the API/zod/engine contract (`Move.action.type` / `Move.action.targetId`) never sees it. Every attack-staging flow dead-ends at the moves endpoint with a 400, and frontend tests keyed on the state machine (`staged → playerTurnSubmitted`) never fire as written.

2. **Fallback-board debrief flag — documented requirement with no persistence home (gap).**
   - `docs/03-board-generation.md:89`: "Record in the game row that the fallback fired (for stats/debug)."
   - vs. `docs/01-architecture.md:86–98` (games table: no such column) and `docs/06-api-contract.md:52–59` (GameState: no such field).
   - What could go wrong: the phase-4 agent must invent column/DTO/field names, directly violating the no-invention fence in `docs/08-agent-rules.md:7` ("Gaps → stop and ask… Never fill the gap silently").

## AMBIGUITIES

1. **AI turn serialized state — which units appear in the UNITS block?**
   - `docs/04-ai-integration.md:97`: "UNITS: id=class x,y hp/maxHp / your side = enemy, ids start with 'E-'"
   - vs. `docs/04-ai-integration.md:119–122`: sample output includes `P-…` player lines ("… player units occupy rows 13-14…").
   - Interpretation A: block carries both armies (E- = self, P- = valid attack targets). Interpretation B: block is E-only with player targets implied.
   - Two agents could implement wildly different serializers/golden fixtures from this.

2. **Path length semantics in the validator.**
   - `docs/02-game-rules.md:27`: "path[0] = current tile … path.at(-1) = final tile"
   - `docs/02-game-rules.md:50–53`: rejection kinds include `"path length 4 exceeds movement 3"`.
   - Interpretation A: array length counts tiles (final = length−1 ⇒ a 3-tile move = length 4, so the message means something else). Interpretation B: length counts moves. The doc's own example collides with its own path semantics — implementers will split differently.

3. **Statistics response shape — the "totals row".**
   - `docs/05-frontend.md:106`: "Totals card (games, win rate big numerals) + the per-difficulty table"
   - `docs/06-api-contract.md:120–131`: flat object `{ gamesPlayed, wins, losses, winRate, byDifficulty }` — no explicit "totals" key shown.
   - Interpretation A: "totals row" = the flat top-level stats. Interpretation B: there is a separate totals grouping not present in the example.

## CONTRADICTIONS

1. **Response envelope — one doc, two rules.**
   - `docs/06-api-contract.md:8`: "…with a JSON body per endpoint below (no envelope — the body IS the resource)."
   - vs. `docs/06-api-contract.md:79–80`: `200 {"games":[GameSummary, …]}` and `docs/06-api-contract.md:10–11`: `201 → {"game": GameState}`.
   - A hostile implementer cannot satisfy both; client and server could silently diverge on every game endpoint.

2. **Weapon triangle — permission vs. prohibition.**
   - `docs/00-project-overview.md:95`: "…possibly shipped silently as an undocumented 'secret' advantage."
   - vs. `docs/00-project-overview.md:93–94` (Later hooks: "do NOT build now, do not design around") and `docs/08-agent-rules.md:31` ("Do not anticipate later-hooks features (hidden triangle, …)").
   - An agent could read the "secret advantage" phrasing as license to build it.

3. **End-turn confirm dialog — two different specs.**
   - `docs/05-frontend.md:86`: "…button always enabled, confirm dialog only when un-acted units remain."
   - `docs/06-api-contract.md:166`: "…wait-vs-omit is a real distinction the END-TURN CONFIRM DIALOG keys on."
   - Trigger and semantics of the same dialog are described differently.

## VERDICT

1. **06's response-envelope contradiction** (`no envelope` vs `{"game":...}` / `{"games":[...]}`) — highest severity; the API contract is internally unsatisfiable and blocks all endpoint implementation.
2. **The staged-move action-shape mismatch** (`attack:target` vs `action.type`/`targetId`) — the core combat loop cannot be built without resolving it.
3. **The fallback-board debrief flag** (mandated in `03`, absent in schema/DTO) — forces agents to invent, against the project's own fence.
